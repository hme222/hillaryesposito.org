## Interactive Reference Scan
Verified on: 2026-08-27
Refresh by: 2026-11-25
Brief need: Preserve the approved MSK complexity-to-clarity system map and the Home hero's user-initiated three-row-to-five-row evidence disclosure without turning portfolio proof into spectacle.

### Three.js — Use
Source: `https://threejs.org/examples/`, `https://threejs.org/examples/?q=particle`, and `https://threejs.org/manual/en/creating-a-scene.html`
Pattern: A bounded spatial scene whose visual state changes with user progress; current official examples prominently include WebGPU/TSL particles and compute scenes, while the manual requires an explicit camera, renderer, animation loop, responsive sizing, and performance restraint.
Evidence status: Official
Purpose: Keep the existing MSK system map's scroll-linked transformation from tangled workflow to ordered blueprint; the transformation explains a project relationship that flat ornament would not.
STEAL: One purposeful spatial transformation, capped rendering cost, paused offscreen work, static resolved reduced-motion state, and explicit disposal.
IGNORE: WebGPU particles, continuous ambient animation, cinematic cameras, shaders, and 3D hero decoration unrelated to recruiter evidence.
Risk: GPU and battery cost, WebGL unavailability, device heat, canvas exclusion from the accessibility tree, and degraded low-power behavior.
Fallback: The map is decorative (`aria-hidden`); the adjacent semantic narrative remains complete. Reduced motion renders the resolved state without scroll animation, and WebGL construction failure leaves the narrative intact.
Decision reason: Use is limited to the already-implemented MSK explanatory map. Do not extend Three.js to the Home disclosure or other proof surfaces.

### GSAP — Reject
Source: `https://gsap.com/showcase/`, `https://demos.gsap.com/`, `https://gsap.com/docs/v3/Plugins/ScrollTrigger/`, and `https://gsap.com/docs/v3/GSAP/gsap.context()/`
Pattern: ScrollTrigger scrub/pin choreography, timelines, UI transitions, FLIP-style work, and React-scoped cleanup.
Evidence status: Official
Purpose: Candidate for coordinating complex multi-scene scroll narratives.
STEAL: Explicit lifecycle cleanup, scoped animation ownership, and a single timeline when a future approved story genuinely requires coordinated stages.
IGNORE: pinned storytelling, magnetic/cursor effects, scrubbed galleries, text spectacle, and long scroll capture.
Risk: A second animation runtime, duplicated IntersectionObserver/scroll behavior, more cleanup paths, and a louder interaction register than the evidence-first brief permits.
Fallback: Existing React state, CSS keyframes/transitions, IntersectionObserver, and reduced-motion media queries.
Decision reason: The current build has no multi-scene timing problem. Adding GSAP would duplicate tested native behavior and increase research, bundle, and maintenance cost.

### Motion — Reject
Source: `https://motion.dev/examples`, `https://motion.dev/examples/js-scroll-triggered`, and `https://motion.dev/docs/react-layout-animations`
Pattern: Layout/shared-view transitions, `inView` scroll-triggered reveals, spring gestures, and compact state animations.
Evidence status: Official
Purpose: Candidate for animating the Home queue's layout expansion and existing restrained reveals.
STEAL: Motion should explain layout relationship and state change; cleanup and reduced-motion behavior remain first-class.
IGNORE: spring bounce, cursor effects, page wipes, scroll zoom, and animation that becomes the evidence carrier.
Risk: The package is already present but unused in source; importing it for one disclosure would create runtime cost and a parallel motion system. Current JavaScript `animateLayout` guidance is also early-access/Motion+ and is not appropriate for this production slice.
Fallback: The implemented native button, conditional DOM rows, CSS stagger, max-height transition, instant reduced-motion state, and existing scroll-reveal hook.
Decision reason: Reject adoption for this slice. The scan changed the open dependency decision from “use a library for polished expansion” to “keep the approved React/CSS implementation and add no Motion import.”

Selected pattern(s): Existing Three.js complexity-to-clarity map; native user-initiated layout disclosure; restrained native scroll reveal.
Rejected pattern(s): GSAP scroll choreography and Motion-powered layout animation because neither solves an unmet brief need; Three.js particles/hero scenes because they would compete with evidence and cost more on low-power devices.
Dependency decision: Existing `three` only for the already-bounded MSK map. No GSAP dependency and no new Motion runtime use for this slice. `framer-motion` remains an existing package-management question outside this proof; do not import it merely because it is installed.
